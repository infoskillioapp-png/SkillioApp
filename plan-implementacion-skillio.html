2. Tus 2 dudas técnicas, resueltas

SÍ¿Créditos en PRO + contador en free, conviviendo?
Es la opción más limpia. Cada ruta de IA hace: if (plan === "pro") → lógica de créditos; else → contador de 3. No conviene unificar: cada modelo cumple un rol distinto (free = prueba, PRO = saldo mensual).
SÍ¿Ocultar el contador en free y que vea 0 créditos?
Free arranca con credits = 0 (visible) + un contador interno invisible free_generations_used (0→3). Al pagar se le cargan los 500. El chip de créditos muestra lo que tiene: free ve 0, PRO ve su saldo real.
⚠️ Riesgo de UX que te dejo anotado
Si el free ve "0 créditos" puede pensar "no puedo hacer nada" y ni intentar. Se implementa como pediste, pero queda la opción de mostrar "Probá gratis" en vez del 0 pelado si querés bajar ese riesgo.

4. WhatsApp OTP — explicado (y por qué lo diferimos)

PreguntaRespuesta
¿Cómo funciona?El usuario pone su teléfono → le mandás un código por WhatsApp → lo escribe → queda verificado. 50 gmails truchos es fácil; 50 teléfonos no.
¿Por Clerk o aparte?Clerk hace OTP por SMS nativo, pero WhatsApp puntual NO. Necesitás un proveedor: Twilio Verify (lo más fácil, canal WhatsApp + fallback SMS) o WhatsApp Cloud API de Meta.
¿Tu número o otro?Ni tu celular ni manual. Se usa un número de WhatsApp Business API dedicado, vía el proveedor.
¿Riesgo de ban?Con API oficial → cero riesgo. El ban solo pasa si automatizás tu WhatsApp personal con librerías truchas (whatsapp-web.js, Baileys).
¿Es gratis?No. Cada verificación cuesta centavos (Twilio ~USD 0,05; Meta cobra por conversación de "autenticación", barato en Argentina pero no $0).
Recomendación
Con 2 registros/día, el OTP de WhatsApp es prematuro. Arrancamos con email/Google de Clerk. Si el farmeo de las 3 gratis se vuelve un problema real, lo sumamos (Twilio Verify es el camino más corto). No tiene sentido pagar por mensaje + agregar fricción antes de tener tráfico.
